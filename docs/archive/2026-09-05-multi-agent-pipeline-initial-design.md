## 사용자 질문

> 설계는 클로드 코드 opus, 구현은 antigravity cli gemini flash 3.8, 리뷰는 codex gpt5.6 형태로 멀티 ai 코딩 에이전트 환경을 구축하고 싶은데 의견 부탁.

## 답변

### 총평

역할 분담 자체는 타당합니다. 다만 이 구조는 **"설계 산출물의 명세 밀도"** 하나에 성패가 걸립니다. Flash급 모델에게 구현을 맡긴다는 건 *판단을 위임하지 않는다*는 뜻인데, 대부분의 사람이 설계 단계에서 "무엇을 만들지"만 쓰고 "어떻게 만들지"는 비워둡니다. 그러면 Flash가 그 빈칸을 창의적으로 채우고, 리뷰 단계에서 그걸 잡느라 GPT 토큰을 태우고, 결국 재설계로 되돌아옵니다. 핑퐁 비용이 Opus로 그냥 구현했을 때보다 커지는 지점이 실제로 존재합니다.

그리고 전제 하나: **세 CLI는 컨텍스트를 공유하지 않습니다.** 유일한 공유 상태는 파일시스템과 git입니다. 이걸 설계의 출발점으로 삼아야 합니다.

---

### 1. 공유 상태 규약

레포 안에 에이전트 간 통신 채널을 파일로 고정합니다.

```
.ai/
  specs/    <task-id>.md      # Opus 산출 — 구현자의 유일한 입력
  impl/     <task-id>.md      # Flash 산출 — 구현 노트, 이탈 사항
  reviews/  <task-id>.md      # Codex 산출 — 심각도 분류된 지적
  state.md                    # 현재 태스크 상태 (design/impl/review/done)
```

각 에이전트는 **자기 단계의 입력 파일만 읽고, 자기 출력 파일만 씁니다.** 이걸 각 CLI의 프로젝트 지침(`CLAUDE.md`, `GEMINI.md`/`AGENTS.md`, `AGENTS.md`)에 못 박아두세요. 안 그러면 Flash가 리뷰 파일을 읽고 스스로 판단하기 시작합니다.

---

### 2. 파이프라인과 게이트

```
[Opus 설계] → spec.md
      ↓
[Flash 구현] → 코드 + impl.md
      ↓
[결정론적 게이트]  build / typecheck / test / lint   ← AI 아님, 여기서 먼저 거름
      ↓ (통과할 때까지 Flash 자체 루프, 최대 3회)
[Codex 리뷰] → review.md (심각도 분류)
      ↓
  BLOCKER/MAJOR 있음? → Flash 수정 (같은 지적 2회 반복 시 → Opus 에스컬레이션)
  SPEC-VIOLATION 있음? → 즉시 Opus 에스컬레이션 (설계 결함 가능성)
      ↓
  done
```

**결정론적 게이트를 AI 리뷰 앞에 두는 게 핵심입니다.** 컴파일도 안 되는 코드를 GPT에게 high effort로 읽히는 건 순수 낭비입니다. Flash 단계에서 `pnpm test` 같은 명령이 통과할 때까지 자체 루프를 돌리게 하고, 그 명령어를 spec에 명시하세요.

---

### 3. 설계 산출물 템플릿 (가장 중요)

Opus가 이 형식으로만 출력하도록 고정합니다.

````markdown
# <task-id>: <제목>

## 배경 (구현자는 이전 대화를 모른다 — 여기에 다 적는다)
## 범위 밖 (건드리지 말 것)

## 변경 대상 파일
- `src/a.ts` — 수정: X 함수에 Y 추가
- `src/b.ts` — 신규
- 이 목록 밖의 파일은 생성/수정 금지

## 시그니처 (그대로 쓸 것, 임의 변경 금지)
```ts
export function foo(input: Bar): Result<Baz, FooError>
```

## 동작 명세
- 정상 경로: …
- 엣지 케이스: 입력이 빈 배열이면 → …
- 에러 처리: 네트워크 실패 시 → 재시도 없이 FooError.Network 반환

## 기존 코드 참조
- 유사 패턴은 `src/existing.ts:42` 를 따를 것

## 인수 조건 (통과해야 완료)
- [ ] `pnpm typecheck` 통과
- [ ] `pnpm test src/foo.test.ts` 통과
- [ ] 신규 테스트: 빈 입력 / 정상 / 네트워크 실패 3케이스

## 판단이 필요하면
구현하지 말고 `.ai/impl/<task-id>.md` 에 QUESTION 으로 남기고 중단할 것
````

마지막 항목이 Flash의 침묵 실패(명세와 다르게 구현하고 "완료" 보고)를 막는 유일한 장치입니다.

---

### 4. 리뷰 산출물 규약

Codex에게 자유 서술을 허용하면 스타일 지적이 절반을 차지합니다. 분류를 강제하세요.

```markdown
## SPEC-VIOLATION   # 명세와 다르게 구현 → Opus 에스컬레이션
## BLOCKER          # 동작 오류, 데이터 손실, 보안
## MAJOR            # 엣지 케이스 누락, 리소스 누수
## MINOR            # 가독성 — 기록만, 수정 요청 금지
```

그리고 각 지적에 **재현 시나리오(입력 → 잘못된 출력)를 필수로** 요구하세요. 이게 없으면 추측성 지적이 통과합니다. MINOR를 수정 대상에서 제외하는 게 핑퐁 방지에 생각보다 크게 작용합니다.

---

### 5. Effort 레벨

버전 번호(Flash 3.8 / GPT-5.6)는 지식 범위 밖이라 플래그 이름은 각 CLI의 최신 문서로 확인 필요. 아래는 역할 기준 권장치.

| 단계 | 모델 | Effort | 근거 |
|---|---|---|---|
| 설계 (신규 기능·아키텍처) | Opus | **high** | 되돌리기 비용이 가장 큰 단계. 여기서 아끼면 하류 전체가 비쌈 |
| 설계 (정형 작업: CRUD 추가, 기계적 리팩터링) | Opus | **medium** | 패턴이 이미 레포에 있으면 high는 과함 |
| 구현 | Flash | **low ~ medium** | 아래 설명 참조 |
| 테스트 작성·디버깅 | Flash | **medium ~ high** | 실패 원인 추론은 구현보다 추론 깊이가 필요 |
| 리뷰 (초회) | Codex | **high** | 리뷰는 "어떻게 깨질까"를 상상하는 작업 — 추론 예산이 품질에 직결 |
| 리뷰 (수정 후 재확인) | Codex | **low ~ medium** | diff가 작으면 high는 낭비 |
| 에스컬레이션 중재 | Opus | **high** | 설계 vs 구현 충돌 판단 |

**구현 단계에 low를 권하는 이유**가 직관에 반할 수 있는데: 작은 모델은 추론 예산을 올리면 "더 나은 방법"을 탐색하기 시작합니다. 명세를 벗어난 리팩터링, 임의의 추상화 추가, 시그니처 변경 같은 게 여기서 나옵니다. 명세가 촘촘하다면 구현은 거의 받아쓰기 작업이므로 low로 충분하고, 오히려 이탈이 줄어듭니다.

**단, 이건 명세 밀도에 대한 베팅입니다.** 초기 2~3주는 medium으로 시작해서, spec 품질이 안정된 걸 확인한 뒤 low로 내리세요. 반대로 Flash가 계속 QUESTION을 남기거나 이탈한다면 effort를 올릴 게 아니라 **spec 템플릿을 고쳐야 한다**는 신호입니다.

---

### 6. 에스컬레이션 규칙

핑퐁 무한루프가 이 구조의 가장 흔한 실패입니다. 상한을 숫자로 정하세요.

- 같은 지적이 리뷰에서 **2회 반복** → Flash로는 못 고침. Opus로 넘김
- Flash 자체 게이트 루프 **3회 실패** → Opus로 넘김
- `SPEC-VIOLATION` 발생 → 즉시 Opus. 구현자 잘못이 아니라 명세 결함일 확률이 높음
- 한 태스크의 총 라운드 **5회 초과** → 사람이 개입

---

### 7. 다르게 하겠는 지점 하나

**최종 승인(merge gate)을 Codex가 아니라 Opus에 두는 걸 고려.** "구현이 설계 의도와 일치하는가"는 설계자가 가장 잘 판단합니다. 다만 매 태스크마다 Opus를 부르면 비용 이점이 사라지므로, 절충안:

- Codex 리뷰에 `SPEC-VIOLATION` 섹션이 **비어 있으면** → Opus 호출 없이 머지
- 비어 있지 않으면 → Opus가 spec 원본과 diff를 놓고 판단 (구현을 고칠지, 설계를 고칠지)

즉 Opus는 상시 게이트가 아니라 **조건부 중재자**로 둡니다.

---

### 8. 시작 방법

전체를 한 번에 자동화하지 말 것. 권장 순서:

1. **1주차 — 수동 릴레이.** 세 CLI를 각각 열고 `.ai/` 파일을 손으로 넘기며 5~10개 태스크를 돌립니다. 목적은 자동화가 아니라 **spec 템플릿을 실전에서 교정**하는 것. 어떤 항목이 비면 Flash가 이탈하는지가 여기서 드러남.
2. **2주차 — 게이트만 스크립트화.** 결정론적 검증(build/test/lint)과 상태 전이만 PowerShell 스크립트로. 모델 호출은 여전히 수동.
3. **3주차 이후 — 오케스트레이션.** 그때쯤이면 라운드 상한, 에스컬레이션 조건이 경험적으로 정해져 있을 것.

1단계를 건너뛰고 바로 자동화하면, spec 템플릿의 결함이 자동화된 핑퐁으로 증폭되어 원인을 못 찾게 됩니다.
