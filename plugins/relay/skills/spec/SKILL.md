# relay:spec

구현 이슈 본문을 `references/spec-template.md` 형식으로 쓰고, 마지막에 기동 전 검사를 돌린다. 진행자 세션은 띄우지 않는다.

`$RELAY` 는 이 스킬을 불러왔을 때 표시되는 *Base directory* 에서 두 단계 위(플러그인 루트)다 — `python "$RELAY/scripts/relay_cli.py" --help`.

## 쓰는 규칙

정본은 트래커의 구현 이슈다(ADR 0006). 이슈 본문의 형식은 `references/spec-template.md` 다 — 먼저 Read 한다.

- **하위 이슈가 있으면 하위 이슈 하나가 태스크 하나**이고, 트래커의 blocking 이 태스크 의존이다. 하위 이슈가 없으면 이슈 자체가 태스크다(ADR 0007). 태스크는 **5개 이하**다. 넘으면 이슈를 나눈다 — 진행자는 태스크를 쪼개지 않는다.
- 부모 이슈는 Run 의 목표·사람용 개요·하위 이슈 목록만 담는다. 하위 이슈는 각자 자기완결 spec 이다(템플릿 전체). `<base>` 는 적지 않는다 — 진행자가 정한다.
- 이슈는 쓰기 권한자(`OWNER`·`MEMBER`·`COLLABORATOR`)가 쓴다. 다른 사람이 쓴 이슈는 기동 전 검사에서 막힌다.
- **위임 가치가 음수인 태스크를 구분할 것.** spec 에 내용을 전부 적어야 하는 태스크(문서·규범·템플릿 authoring)는 위임하면 같은 내용을 두 번 쓰는 셈이고, 워커의 산출물은 spec 의 전사에 그친다. 이런 태스크는 설계 세션이 직접 쓴다. 위임이 유효한 것은 **spec 이 요구사항이고 산출물이 코드일 때**다.
- **spec 을 쓰기 전에 대상 코드를 직접 읽는다.** 구현을 읽어야 "이상해 보이지만 지금은 건드리면 안 되는 동작"을 미리 찾아낼 수 있고, 그걸 spec 에 "이런 걸 만나면 고치지 말고 `ask`로 물어보라"로 적어둘 수 있다.
- **「사람이 할 일」 절은 하위 이슈가 없으면 이슈 자체에, 있으면 부모에만 둔다.** 하위 이슈에 두면 기동 전 검사가 실패한다.
- **`머지 전:` 은 머지가 곧 배포인 저장소에서만 생긴다.** 시작 전에 할 수 있는 일(도구 설치 등)은 이 절에 적지 않고 handoff 전에 끝낸다. 게이트가 그 일을 전제하면 「배경」에 사실로 적는다(예: "Pester 5 가 설치돼 있다").
- **검사기·파서처럼 입력 경우가 열린 태스크는 다룰 경우를 spec 에 열거하고, 열거하지 않은 경우는 범위 밖이라고 적는다.** 근거: 리뷰어가 라운드마다 놓친 경우를 새로 찾아 라운드가 길어진 사례가 있었다.

## 일괄 진행

- 함께 돌릴 구현 이슈는 blocking 으로 잇는다. 의존이 없어도 같은 진행 목록에 넣으려면 blocking 하나를 건다. 다른 저장소 이슈와 잇지 않는다.
- 하위 이슈의 blocking 은 형제 하위 이슈끼리만 건다.
- `머지 전:` 에 할 일이 있는 이슈가 진행 목록에 있으면 일괄 진행은 시작하지 않는다. 머지 뒤로 옮길 수 있으면 옮긴다.
- 여러 이슈를 이었으면 마지막에 `python "$RELAY/scripts/relay_cli.py" batch-plan --issue <URL>` 도 돌린다(읽기만 한다). 시작은 사람이 `/relay:batch <URL>` 로 한다. 모델은 이 스킬을 부를 수 없다.

## 끝내기

`python "$RELAY/scripts/relay_cli.py" handoff-check --issue <이슈 URL>` 을 돌린다. 읽기만 하는 검사다. `FAIL` 이면 `→` 줄대로 이슈를 고치고 다시 돌린다. 통과하면 끝난다. 진행자 세션을 띄우는 것은 `relay:handoff` 다.
