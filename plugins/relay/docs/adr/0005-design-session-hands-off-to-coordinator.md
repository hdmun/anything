# 설계 세션은 진행자 세션에 핸드오프하고 끝난다

ADR 0004 는 설계 세션이 Run 끝까지 떠서 태스크마다 진행자 워커를 띄워 감독하는 2단 구조(워커 중첩 깊이 2)였다. 설계가 wayfinder(구현 이슈 작성)로 빠지면서 설계 세션에 남는 일은 감독과 `ask` 중계뿐이 되었고, 그 감독은 Orca orchestration 이 표준 코디네이터 형태로 이미 제공한다. 그래서 **설계 세션은 구현 이슈를 쓴 뒤 `relay:handoff` 로 진행자 세션을 한 번 띄우고 끝난다.** 진행자 세션은 dispatch 된 워커가 아니라 Run 을 소유한 최상위 코디네이터이고, 구현 이슈의 태스크를 모두 orchestration 으로 돌린다(구현자·리뷰어는 깊이 1). SPEC_VIOLATION·반복 지적·라운드 한도는 진행자가 판정하되, 판정은 high effort 서브에이전트에 맡긴다. 사람의 일은 시작 한 마디, 태스크별 PR 검토, 멈춤 보고 읽기뿐이다.

## Considered Options

- **깊이 2 유지(ADR 0004)**: 진행 루프 컨텍스트를 태스크마다 버리는 장점은 있지만, 중첩 깊이 사전 조건·`ask` 중계·세션 판정이 남고 relay 가 Orca 의 표준 형태가 아닌 중첩 워커 위에 선다. 기각.
- **연쇄 핸드오프(태스크마다 진행자가 다음 진행자를 띄움)**: 컨텍스트는 깨끗하지만 Run 승계(`run-use`)가 검증되지 않았고 핸드오프가 감독 밖에서 반복된다. 기각.
- **판정을 사람에게**: 사람 개입을 결과 검토로 줄인다는 목표와 어긋난다. 기각.
- **진행자 전체를 medium/high effort 로**: 잦은 진행 루프까지 비싸진다. 드문 판정만 서브에이전트로 비싸게 하는 편이 ADR 0004 의 비용 논리(잦은 구간은 싸게, 드문 판단은 비싸게)를 잇는다. 기각.

## Consequences

- relay 스킬은 진행자 역할 하나만 다룬다. Orca preamble 로 세션을 판정하던 절은 사라진다.
- `relay:handoff` 는 설계 세션에서만 쓰는 별도 스킬이다. 스킬 개수 결정(단일 스킬)을 다시 연 근거: relay 는 진행자 세션에서만, handoff 는 relay 를 읽지 않는 설계 세션에서만 쓰여 한 세션에 같이 뜨지 않는다.
- 워커 중첩 깊이 2 사전 조건과 `doctor` 의 `orca:nested-depth` 검사가 필요 없어진다.
- 모델 설정에 판정 서브에이전트 역할이 늘어난다(기본 Opus 계열 high). 진행자 세션은 Opus 계열 low 로 루프를 돈다.
- 진행자 한 명이 이슈의 태스크를 모두 돌므로 컨텍스트가 쌓인다. 구현 이슈를 태스크 몇 개 이하로 작게 잡아 감당한다. **재검토 조건**: 진행자 컨텍스트 누적이 실제로 문제로 측정되면 연쇄 핸드오프를 다시 본다.
