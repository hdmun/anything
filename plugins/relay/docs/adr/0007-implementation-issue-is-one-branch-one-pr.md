# 구현 이슈 하나가 브랜치·PR 하나이고, 하위 이슈가 태스크다

ADR 0005 로 진행자 세션 하나가 구현 이슈의 태스크를 모두 돌게 되면서, 이슈 안에서 태스크를 어떻게 나누고 어떻게 합칠지를 정해야 했다. **구현 이슈에 하위 이슈가 있으면 하위 이슈 하나가 태스크 하나이고 트래커의 blocking 이 태스크 의존이 된다. 하위 이슈가 없으면 이슈 자체가 태스크 하나다.** 태스크는 DAG 순서대로 **구현 이슈 하나의 브랜치 위에서 차례로** 돌고(각 태스크의 `<base>` 는 그 태스크를 시작할 때의 브랜치 HEAD), PR 은 모든 태스크가 끝난 뒤 하나만 연다. 그래서 ADR 0005 의 「태스크별 PR 검토」는 「구현 이슈별 PR 검토」로 바뀐다. 사람의 일은 시작 한 마디, PR 하나 검토, 멈춤 보고 읽기다.

## Considered Options

- **이슈 하나 = 태스크 하나**(큰 일은 이슈 여러 개 + 핸드오프 여러 번): 사람의 시작 한 마디가 이슈마다 늘어난다. 기각.
- **이슈 본문에 태스크 절을 나눠 적기**: 태스크마다 본문이 따로 없어 spec 스냅숏과 SPEC_VIOLATION 판정 범위가 흐려진다. 기각.
- **태스크별 브랜치·PR, 의존 태스크는 앞 PR 머지를 기다림**(이전 방식): 태스크 5개가 한 줄로 이어지면 사람이 4번 끼어들고, 그동안 진행자가 멈춘다. 기각.
- **스택 PR**: 리뷰 중에 앞 PR 이 바뀌면 뒤 PR 을 줄줄이 rebase 해야 한다. 기각.
- **통합 브랜치 + 태스크 브랜치 머지**(mattpocock `implement-spec`): 병렬 실행을 위한 구조다. relay 는 순차라 브랜치 하나로 충분하다. 병렬 승격(SKILL.md (k)) 때 다시 본다.

## Consequences

- 구현 이슈 하나의 태스크는 **5개 이하**다. 넘으면 이슈를 나눈다. 태스크를 나누는 것은 설계 세션의 몫이고 진행자는 쪼개지 않는다.
- 하위 이슈는 각자 자기완결 spec 이다(relay spec 템플릿 전체). 부모 이슈는 Run 의 목표·사람용 개요·하위 이슈 목록만 담고 스냅숏하지 않으며 리뷰어도 읽지 않는다. PR 제목은 부모 이슈 제목이고, 본문은 부모·하위 이슈를 모두 닫는다.
- relay spec 템플릿은 설계 세션이 읽는 `relay:handoff` 쪽으로 옮긴다. `<base>` 만은 이슈에 적지 않고 진행자가 정한다.
- `relay:handoff` 는 진행자를 띄우기 전에 `relay_cli` 결정기로 태스크 수, 템플릿 필수 절(변경 대상 파일, 인수 조건의 게이트 명령), 작성자 권한(ADR 0006)을 검사한다. 하나라도 어긋나면 띄우지 않는다. 진행자는 스냅숏을 뜰 때 권한만 다시 본다.
- 태스크 ID 는 `I-<이슈 번호>` 다(local-markdown 은 `I-<feature>-<NN>`). spec 스냅숏은 `.ai/specs/<ID>-<슬러그>.md`, 리뷰 리포트는 `.ai/reviews/<ID>.rN.json`, `review.py` 의 `REPORT_RE` 는 `^(I-[a-z0-9-]+)\.r(\d+)\.json$` 이다. 이전 `T-NNN` 파일은 패턴에 맞지 않아 무시되므로 옮기지 않는다.
- 태스크가 중간에 멈추면 끝난 태스크의 커밋은 브랜치에 남는다.
